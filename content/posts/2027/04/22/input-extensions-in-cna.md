CNA preserves the familiar XNA snapshot model: poll `Keyboard`, `Mouse`, `GamePad` and `TouchPanel` during the game loop and compare the current state with the previous frame. The input module also exposes optional extensions for tasks that XNA 4.0 could not represent, from IME composition and relative mouse movement to racing wheels and controller touchpads.

Extension members carry `CNAEXT` and usually an `EXT` suffix. CNA-owned types live under `CNA::Input`, making the compatibility boundary visible in source code.

## Preserve frame semantics

CNA publishes input snapshots at the game-loop boundary. Read them during `Update`, store the previous frame, and derive edges from the pair:

```cpp
const auto keyboard = Keyboard::GetState();
const bool jumpPressed =
    keyboard.IsKeyDown(Keys::Space) && previousKeyboard.IsKeyUp(Keys::Space);
previousKeyboard = keyboard;
```

This remains the foundation even when extensions are enabled. Events are appropriate for committed text, IME composition and device hot-plug, but gameplay actions are usually easier to reproduce when derived from snapshots. Do not update simulation directly from an arbitrary event callback; record the event and consume it at the defined frame boundary.

Mouse relative displacement is consume-on-read. Centralize the read and distribute the resulting snapshot rather than letting several systems poll independently. The same ownership rule avoids one menu, camera or debug overlay accidentally observing a different input moment from the rest of the game.

## Keyboard names and modifiers

`Keyboard::GetState()` remains the normal gameplay API. Extensions fill in the platform-facing details needed by key-binding screens:

```cpp
auto modifiers = Keyboard::GetModStateEXT();
auto name = Keyboard::GetKeyNameEXT(Keys::A);
auto key = Keyboard::GetKeyFromNameEXT(name);
```

Scancode name and conversion functions are also available. They help distinguish a physical key position from the symbol generated by the current keyboard layout. This matters for non-US layouts: movement bindings may care about location, while text entry must follow the user's locale and IME.

## Text input is not key input

Games should not build text by translating pressed keys themselves. `TextInputEXT` publishes committed UTF-16 code units and separate UTF-8 IME composition updates:

```cpp
TextInputEXT::TextInput += [](SharpRuntime::charcs c) {
    AppendUtf16CodeUnit(c);
};

TextInputEXT::TextEditing += [](const std::string& draft, int start, int length) {
    ShowComposition(draft, start, length);
};

TextInputEXT::SetInputRectangle(textBoxBounds);
TextInputEXT::StartTextInput();
```

A code point outside the Basic Multilingual Plane arrives as a UTF-16 surrogate pair, matching FNA's event semantics. Composition offsets come directly from the platform IME and must not be blindly treated as UTF-8 character counts. `TextEditingCandidatesEXT` can expose CJK candidate lists, including the selected item and layout direction.

`StartTextInputWithTypeEXT` supplies a hint such as numeric or password input to an on-screen keyboard. Availability and keyboard visibility still depend on the platform.

## Mouse control beyond absolute coordinates

`Mouse::setIsRelativeMouseModeEXTProperty(true)` changes motion to deltas, the usual mode for a first-person camera. In relative mode, position warping is intentionally not the way to recenter the pointer. `SetCaptureEXT` requests events outside the window, while `GetGlobalPositionEXT` and `WarpGlobalEXT` handle desktop coordinates on platforms that permit them.

These operations are capability-sensitive. Wayland, browsers and terminals impose different rules from a classic X11 or Windows desktop. A game should make pointer capture an interaction state and recover cleanly when focus or permission is lost.

## Modern gamepads

The standard XNA state and vibration calls cover common controllers. CNA adds metadata and hardware features exposed by modern platform backends:

- GUID, name, path, serial and firmware information;
- wired or wireless connection state and battery percentage;
- physical face-button labels;
- player-index LED assignment and light-bar color;
- trigger vibration;
- gyro and accelerometer readings;
- touchpad count, finger capacity, position and pressure;
- Steam Input handle where applicable.

Every query has a safe unavailable value or boolean result. A controller without a gyro should not produce a zero vector that looks like valid data. Keyboard-to-gamepad emulation for Player One is available as an explicit, process-wide option and remains off by default.

Controller slots are not permanent identities. A disconnect can empty one slot and a later device may occupy it. Save bindings by a suitable GUID or device profile where possible, but still let the player confirm the active device. Button-label queries allow prompts to say A/B, Cross/Circle or another physical convention without changing the semantic action bound to that button.

Dead zones also belong to input policy. CNA provides the XInput-derived left-stick, right-stick and trigger thresholds plus `ExcludeAxisDeadZone`, while `GamePad::GetState` can apply the XNA dead-zone modes. Apply a dead zone once; stacking another hidden filter in an action layer can make controls feel unresponsive and makes controller comparisons difficult.

## Raw joysticks and force feedback

An Xbox-shaped `GamePadState` cannot describe every flight stick, throttle, arcade controller or racing wheel. `CNA::Input::Joysticks` enumerates raw devices and exposes their unmapped axes, buttons, hats and trackballs. Connected and disconnected events carry stable platform device identifiers.

```cpp
for (const auto& joystick : CNA::Input::Joysticks::GetJoysticksEXT())
{
    auto capabilities = CNA::Input::Joysticks::GetCapabilitiesEXT(joystick.id);
    auto state = CNA::Input::Joysticks::GetStateEXT(joystick.id);
    // Interpret axes and buttons according to this game's device profile.
}
```

A device may appear both as a mapped gamepad and as a raw joystick; these are two views of the same hardware, not two players.

Raw axes have no universal meaning. Axis zero may be a wheel on one device and a stick on another; ranges, inversion and resting values can also differ. A robust game supplies a calibration screen and stores a profile that maps device controls to game actions. Hot-plug callbacks tell that screen when to refresh, while the simulation continues using its last valid assignment or pauses cleanly.

`CNA::Input::Haptics` opens a standalone force-feedback device or the haptic side of a joystick or mouse. The move-only `HapticDevice` owns its native handle through RAII. Simple rumble is available alongside uploaded effects, playback, gain, autocenter, pause and status operations. Capability queries are essential: many ordinary gamepads provide rumble but not arbitrary force-feedback effects.

## Devices, sensors, power and clipboard

`InputDevices` enumerates mice, keyboards and touch devices and publishes desktop hot-plug events. This metadata does not change XNA's merged keyboard and mouse state into per-device routing.

`Sensors` enumerates the host's accelerometers and gyroscopes and reports standard units: metres per second squared and radians per second. These are phone, tablet or laptop sensors, distinct from `GamePad::GetGyroEXT`. Desktop enumeration is often empty; browser sensor access is permission-gated.

The input module also contains lightweight `Power` and `Clipboard` extensions. `Power::GetInfoEXT` returns battery state, percentage and remaining seconds. `Clipboard` supports UTF-8 text, the Unix primary selection and, where available, typed MIME data such as PNG or HTML. Browser clipboard calls are subject to user gestures and permissions.

## Platform behavior is part of the API

Windows, Linux, macOS, Android, iOS and the browser do not grant identical input control. Relative mouse capture, cursor warping, clipboard MIME types, sensors, haptic effects and device enumeration all vary. CNA documents those differences and returns absence or failure instead of emulating hardware that is not present.

The repository's input demo exercises text entry, relative mouse mode, pointer warp, four gamepad slots, vibration, light bars, motion sensors, touch and gestures. It is a useful first test on a new platform or controller.

For release testing, cover more than the developer's primary keyboard and gamepad. Test a non-US layout, focus loss while keys are held, controller removal during vibration, two simultaneous controllers, an IME composition, mouse capture cancellation and a platform with no optional sensor or haptic service. These cases expose lifecycle errors that a normal movement test cannot.

The guiding rule is simple: keep the compact XNA snapshot API for ordinary gameplay, then opt into a narrowly named extension when the game genuinely needs more information. That preserves portable code while still making modern input hardware accessible.
