`SpriteBatch` turns many high-level sprite and text submissions into renderer work. It is easy to use, but its performance and correctness depend on what happens between `Begin` and `End`: sorting, state selection, texture binding, buffer construction and flushes.

```cpp
spriteBatch.Begin(SpriteSortMode::Deferred,
                  BlendState::AlphaBlend,
                  SamplerState::PointClamp);
for (const Sprite& sprite : visibleSprites)
    spriteBatch.Draw(*sprite.texture, sprite.position, sprite.color);
spriteBatch.End();
```

One `Begin`/`End` pair does not guarantee one native draw. Texture changes, capacity, clipping or effect passes may split work. Conversely, thousands of sprites can remain cheap when they share state and atlas pages.

## Sort modes are semantic choices

`Deferred` records submissions and normally preserves their order until `End`. It is a strong default for transparent 2D scenes whose painter's order matters. `Immediate` submits as calls arrive and is useful when parameters or state intentionally change between individual sprites, but it sacrifices batching opportunities.

Texture sorting groups by texture and can reduce bindings, but it is allowed to change overlap order. It is correct only when overlap does not matter or depth/state makes it unambiguous. Front-to-back and back-to-front require meaningful layer depth on every draw. Equal-depth ordering should not be used as an undocumented tie breaker.

Build a fixture with overlapping translucent red, green and blue sprites. Run every proposed mode and compare the center pixel. If an optimization changes it, the original order was part of the image.

## What breaks a batch

State passed to `Begin` describes a coherent pass: blend, sampler, depth, rasterizer, effect and transform. Changing that contract means ending the pass or using an explicitly supported immediate route. Repeatedly ending for individual objects is often the actual performance problem.

Texture switches can split native work even inside one logical batch. Atlas art that is commonly drawn together, pad atlas entries and keep sampler policy consistent. A font usually references one or more texture pages and participates in the same batching constraints.

Scissor changes are another boundary. For nested UI clips, intersect rectangles, group content under each clip, and restore rasterizer/scissor state after `End`. Render-target changes always define a larger pass boundary.

## Vertices generated by a sprite

A sprite becomes a quad with position, texture coordinates, color and depth. Source rectangle, origin, scale, rotation and `SpriteEffects` determine its four corners and UVs. Negative scale, flipping and rotated origins deserve explicit tests because a symmetric texture hides swapped corners.

Premultiplied alpha is the normal XNA-style path. Vertex color multiplies sampled color. If a white sprite with half-alpha produces a dark fringe, inspect content premultiplication and blend state before changing vertex color math.

Custom effects must accept the vertex contract and texture binding used by SpriteBatch. Update effect parameters at the time required by its sort mode. With deferred submission, mutating one shared effect repeatedly before `End` may not preserve a distinct value for every recorded sprite; use appropriate batching or encode per-sprite data in supported vertices/content.

## Instrument before optimizing

Expose these counters per pass:

```text
submitted sprites: 18,420
native draws:       37
texture switches:   31
effect passes:       1
buffer flushes:      5
scissor changes:     4
```

A large sprite count with few draws may already be fine. Many `Begin`/`End` pairs or texture switches suggest organizational work. High overdraw requires scene/layout changes rather than fewer API calls.

Profile a representative crowded screen, not an empty menu. Preserve a screenshot while changing atlases or sort keys. Record CPU submission and renderer time separately: batching can reduce CPU overhead while fill rate remains the bottleneck.

## A maintainable frame structure

Use named passes such as opaque background, world sprites, particles, lighting composite and UI. Each pass declares target and state once. World passes take a camera transform; UI uses screen or virtual coordinates. Diagnostics report each pass independently.

Qualification should include atlas edges under point/linear sampling, thousands of sprites, multiple fonts, transparent overlap, depth sorting, custom effect, render-target texture, nested scissor and resize. The best SpriteBatch optimization is a frame whose state transitions are intentional enough to explain before a profiler is opened.

## Common visual failures

Dark/bright transparent edges: content alpha convention and blend state disagree. Neighboring atlas colors: padding/filter/addressing wrong. Text/sprites clipped after one panel: scissor/rasterizer leaked. World UI moves with camera: wrong transform batch. Only custom effect wrong: its vertex input, texture unit or deferred parameter lifetime differs.

Reduce to one sprite on impossible-color clear. Test source corners, vertex color white, no rotation, then restore features one by one. Inspect generated batch counters and selected effect. Never solve a state leak by reordering unrelated draws.

## Capacity and lifetime

SpriteBatch owns/reuses internal CPU/GPU buffers under device lifetime. Applications should reuse the object rather than construct per frame. Very large submissions may flush capacity safely; capacity flush should not change order/pixels. Stress beyond one buffer and compare with small reference.

Textures/effects/targets must remain alive until deferred submission is consumed according to CNA's lifetime rules. Do not destroy temporary texture/effect immediately after `Draw` before `End`/backend completion unless the contract owns a reference.

Release evidence stores pass-by-pass screenshot plus submitted sprites, native draws, texture/state switches and CPU time in a crowded real scene. Optimization claims compare identical output and workload. A lower draw count that changes transparent order or samples the wrong atlas is a failed optimization.
